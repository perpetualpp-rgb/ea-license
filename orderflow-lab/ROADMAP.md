## 1. ตอนนี้มีอะไรแล้ว

| ส่วน | สถานะ | ข้อจำกัด |
|---|---|---|
| engine คำนวณ (CVD, กำแพง, ไม้ใหญ่, profile, VWAP) | มีทั้ง Python (`engine/`) และ JS (`web/engine.js`) ผลตรงกันทุกตัวเลข (มีเทสต์) | — |
| หน้า desk (`desk/`) | ใช้งานส่วนตัวได้ กราฟเลื่อน/ซูมแบบ TradingView, แผนเทรด, บันทึกผล | ดึงข้อมูลผ่าน connector ของ claude.ai ในบัญชีเจ้าของ **ขายให้คนอื่นไม่ได้** ข้อมูลเริ่มใหม่ทุกครั้งที่เปิดหน้า |
| collector ระยะ 0 (`live/`) | WebSocket ของ Binance: trades, order book, แท่ง 1 นาที, mark/funding, OI, liquidation · ต่อใหม่และดึงรายการที่ขาดย้อนหลังเอง · มีเทสต์ | ต้องรันบนเครื่องที่ Binance ไม่บล็อก (เครื่องทดสอบของเราถูกบล็อก ฝั่ง futures ทดสอบด้วย unit test) |

ข้อสรุปสำคัญ: แอปสำหรับลูกค้าต้องมี **server ของเราเอง** ที่เก็บข้อมูลตลอด 24 ชม.
และส่งผลคำนวณให้ลูกค้า ลูกค้าไม่ควรดึงข้อมูลจาก exchange เองทีละคน

## 2. สถาปัตยกรรมเป้าหมาย

```
Binance WebSocket ──► Collector (Python asyncio, 24 ชม.)
  aggTrade, depth diff,      │  สร้าง order book ในหน่วยความจำ
  kline 1m, markPrice        │  ใช้ engine/ เดิมคำนวณกำแพง, ไม้ใหญ่, CVD, footprint
Binance REST (OI ทุก 1 นาที) │  คำนวณเหตุการณ์ (กำแพงใหม่/ถูกถอน, ไม้ใหญ่, OI พุ่ง) ตลอด 24 ชม.
                             ▼
                 ฐานข้อมูล time-series (TimescaleDB)
                 trades, book ราย 1 วิ (รวมเป็นช่วงราคา), wall events, OI, liquidation
                             │
                 API + WebSocket gateway (FastAPI)
                 ตรวจสิทธิ์สมาชิก (JWT) ก่อนส่งข้อมูลทุกครั้ง
                             │
          เว็บแอป / PWA (ใช้หน้า desk เดิม + Lightweight Charts)
          ระบบสมาชิก + จ่ายเงิน + แจ้งเตือน (Telegram / LINE)
```

เหตุผลของแต่ละทางเลือก:

* **Python + engine เดิม** มีเทสต์ 51 ข้อ และ engine.js ฝั่งหน้าเว็บให้ผลตรงกัน จึงไม่ต้องเขียนใหม่
* **TimescaleDB (PostgreSQL)** ฐานเดียวเก็บได้ทั้งข้อมูลตลาดและข้อมูลสมาชิก เหมาะกับทีมคนเดียว
  ถ้าข้อมูลเกินราว 50 ล้านแถวต่อวัน ค่อยย้ายเฉพาะ trades ไป ClickHouse
* **WebSocket gateway ของเราเอง** ลูกค้าทุกคนเห็นข้อมูลชุดเดียวกัน ไม่ชน rate limit ของ exchange
  และคุมสิทธิ์ตามแพ็กเกจได้
* **ระบบสมาชิกแบบ managed** (เช่น Supabase Auth) รองรับ email / Google และต่อ LINE Login ผ่าน
  OpenID Connect ได้ ไม่ต้องเขียนระบบรหัสผ่านเอง

### ปริมาณข้อมูลโดยประมาณ (วัดจาก Binance วันที่ 16–18 ต.ค. 2026)

| ข้อมูล | ปริมาณ | พื้นที่ต่อเดือน (หลังบีบอัด) |
|---|---|---|
| XAUUSDT trades | 3,000–26,000 รายการ/ชม. วันหยุด, 45,000–100,000 รายการ/ชม. วันทำการ | ~0.5 GB (วัดได้ ~8 ไบต์/รายการหลังบีบอัด) |
| BTCUSDT trades (spot + futures) | spot 22,000–110,000 รายการ/ชม., futures มากกว่าหลายเท่า | ~1–3 GB |
| order book รวมเป็นช่วงราคา ทุก 1 วิ (ช่วง ±1%) | ~3 KB/วิ ก่อนบีบอัด ต่อสินทรัพย์ | ~0.3 GB ต่อสินทรัพย์ (วัดได้ ~9 MB/วัน) |

เครื่อง 4 vCPU / 8 GB RAM / ดิสก์ 160 GB พอสำหรับ 2–4 สินทรัพย์ในปีแรก

## 3. แผนเป็นระยะ

### ระยะ 0: เก็บข้อมูล 24 ชม. (สัปดาห์ที่ 1–2) ← เริ่มแล้ว 18 ต.ค. 2026
ยิ่งเริ่มเก็บเร็ว ยิ่งมีข้อมูลจริงไว้ทดสอบเครื่องมือ

1. ✅ collector แบบ WebSocket (`live/`) สำหรับ XAUUSDT perp, BTCUSDT perp และ BTCUSDT spot:
   aggTrade, depth diff ที่ซิงก์กับ snapshot, kline 1m, mark/funding, OI ทุก 1 นาที, liquidation
2. ✅ ต่อใหม่อัตโนมัติ, gap ledger ที่ดึงรายการซื้อขายที่ขาดย้อนหลังและลองใหม่จนครบ (ช่วงที่กู้ไม่ได้บันทึกชัด),
   fsync + manifest/sha256 ของไฟล์ที่บีบอัด, `status.json`, รายงานความครบเทียบช่วงเวลาที่ควรเก็บ (`live.check`)
3. ⬜ หาเครื่องที่ Binance ไม่บล็อกและเปิดรันตลอด (คอมที่บ้านในไทย หรือ VPS ที่ทดสอบ ping ผ่าน)
4. ⬜ สำรองข้อมูลทุกวัน และแจ้งเตือนเมื่อ collector หยุด (Telegram bot)
5. ข้อมูลดิบที่เก็บไว้ทำให้ระยะ 1 replay สัญญาณย้อนหลังได้ จึงไม่ต้องรันแผนบน server ตั้งแต่ระยะนี้

เกณฑ์ผ่าน: 14 วัน UTC ติดต่อกัน ที่ **ทุก market/symbol ผ่านทุกวัน** ตามที่ `python3 -m live.check` วัด
"ขาดไม่เกิน 1%" หมายถึง แยกวัดต่อ stream เทียบกับช่วงที่ควรเก็บ (00:00–24:00 UTC ของวันนั้น) ไม่ใช่ช่วงแถวแรกถึงแถวสุดท้าย:

* **kline:** มีแท่ง 1 นาทีที่ปิดแล้ว ≥ 99% ของนาทีในช่วงนั้น (ตัววัดว่า WebSocket ทำงาน)
* **book:** มีแถว book ≥ 99% ของวินาทีในช่วงนั้น (ช่วง resync นับเป็นขาด)
* **trades:** id ที่กู้ไม่ได้ (`trade_gap`) เป็น 0 และไม่มีช่วงค้างใน gap ledger
* วันที่เป็น N/A (ไม่มีข้อมูลเลย) ถือว่าไม่ผ่าน · % ความต่อเนื่องของ trade id ไม่ใช่ uptime จึงไม่ใช้แทนสองข้อแรก
* stream อื่น (mark, OI, liquidation) ยังไม่มีเกณฑ์ ให้ดูความสดใน `status.json` และอย่าใช้ผ่านเกณฑ์นี้รับรองทั้งระบบ

### ระยะ 1: พิสูจน์ว่าข้อมูลวิเคราะห์มีประโยชน์จริง (สัปดาห์ที่ 3–8)
1. replay ข้อมูลที่เก็บผ่าน engine แล้ววัดว่าเหตุการณ์ที่เครื่องมือแสดงมีผลต่อราคาจริงไหม เช่น
   กำแพงที่ยืนนานถูกราคาเคารพกี่ %, โซนไม้ใหญ่, CVD แยกทางกับราคา, OI + ราคา, liquidation ก้อนใหญ่
2. แยกผลตามสินทรัพย์ ช่วงเวลา (เอเชีย/ลอนดอน/นิวยอร์ก) และช่วงข่าว ใช้ข้อมูลชุดฝึกกับชุดทดสอบแยกกัน
3. เพิ่ม footprint (ซื้อ×ขายรายราคาในแต่ละแท่ง) และการตรวจจับการดูดซับ (absorption)
4. เทียบสัญญาณจาก XAUUSDT กับราคา COMEX ว่าไปทางเดียวกันแค่ไหน

เกณฑ์ผ่าน (ไม่ใช้ "ข้อมูล 4 สัปดาห์ + 3 สัญญาณที่ต่างจากสุ่ม" เป็นเกณฑ์อีกต่อไป):

* **กำหนด hypothesis ล่วงหน้า** ก่อนดูผล: นิยามเหตุการณ์, ตลาด, horizon, ตัววัดผล, ขนาดตัวอย่างขั้นต่ำ และ baseline ที่จะเทียบ
* **แยกข้อมูลตามเวลา** เป็น train / validation / test โดยไม่ให้ lookback หรือ future return ซ้อนกันจนข้อมูลรั่ว
  ใช้ holdout และ **walk-forward** และดูผลแยก regime (วันข่าว ตลาดนิ่ง ตลาดผันผวน)
* **เทียบ baseline** ของ regime เดียวกัน (เช่น เวลาหรือระดับราคาสุ่มที่ห่างจากราคาเท่ากัน)
* **คุม multiple testing**: นับทุกสัญญาณและพารามิเตอร์ที่ลอง ไม่เลือกเฉพาะตัวที่ออกมาดี
* รายงาน **effect size, N และความไม่แน่นอน** (ช่วงความเชื่อมั่น), false positives และผล holdout ที่ไม่ดีด้วย
* แยก event study (เช่น โอกาสแตะระดับใน 15 นาที) ออกจากผลกำไรของกลยุทธ์ และหัก **ต้นทุน** (ค่าธรรมเนียม spread
  slippage funding) ก่อนบอกว่าใช้ทำกำไรได้
* ใช้เฉพาะวันที่ผ่านเกณฑ์คุณภาพข้อมูลของระยะ 0 · ผล parity JS/Python ไม่ใช่หลักฐานทางเศรษฐศาสตร์

ผลนี้ใช้เขียนหน้า "เครื่องมือนี้ช่วยอะไร" แบบมีตัวเลขและข้อจำกัดรองรับ และเลือกฟีเจอร์ที่จะใส่ในแอป

## 4. ความเสี่ยงที่ต้องปิดก่อนเก็บเงิน

ค้นจากแหล่งทางการเมื่อ 18 ต.ค. 2026 บางเว็บ (cmegroup.com, sec.or.th) บล็อกการเข้าถึงอัตโนมัติ
ข้อมูลส่วนนั้นมาจากสำเนาเอกสารหรือสรุปของสำนักงานกฎหมาย ทุกข้อต้องให้ทนายยืนยันก่อนเปิดขาย

### 4.1 ใบอนุญาต ก.ล.ต. (ความเสี่ยงสูงสุด)
* การขาย **แผนเข้า/SL/TP ของ BTC** แบบเก็บเงินเข้าข่าย "ที่ปรึกษาสินทรัพย์ดิจิทัล" ตาม พ.ร.ก.
  ธุรกิจสินทรัพย์ดิจิทัล 2561 ต้องเป็นบริษัทไทย ทุนจดทะเบียนชำระแล้ว ≥ 1 ล้านบาท
  โทษถ้าไม่มีใบอนุญาต (ม.66) จำคุก 2–5 ปี ปรับ 2–5 แสนบาท
  [Tilleke](https://www.tilleke.com/insights/new-digital-asset-business-requirements-for-businesses-in-thailand/) ·
  [Baker McKenzie 2025](https://www.bakermckenzie.com/en/-/media/files/insight/guides/2025/a-complete-guide-to-digital-asset-law-in-thailand-2025.pdf)
* ทองคำฟิวเจอร์ส / CFD / XAUUSDT อยู่ใต้ พ.ร.บ. สัญญาซื้อขายล่วงหน้า 2546 การให้คำแนะนำซื้อขาย
  เป็นทางค้าปกติเข้าข่าย "ที่ปรึกษาสัญญาซื้อขายล่วงหน้า"
* ไม่พบข้อยกเว้นสำหรับคำแนะนำที่สร้างจากโปรแกรม แผนที่คำนวณอัตโนมัติจึงไม่ช่วยให้พ้น
* ใช้กับผู้ให้บริการนอกประเทศที่ขายให้คนไทยด้วย (แก้ไขปี 2568: ดูจากภาษาไทย, รับเงินบาท, โดเมน .th)
  [DFDL](https://www.dfdl.com/insights/content-hub/articles/thailands-digital-asset-law-amended-to-clarify-extraterritorial-reach/)
* การพาผู้ใช้ไปเทรดกับแพลตฟอร์มต่างประเทศที่ไม่มีใบอนุญาตในไทยอาจเข้าข่ายร่วมกระทำผิด
  [ผู้จัดการ 17 ต.ค. 2566](https://mgronline.com/stockmarket/detail/9660000093570)
* **ทางที่เสี่ยงน้อยกว่า:** ขายเป็นเครื่องมือวิเคราะห์ (กำแพง, CVD, OI, ไม้ใหญ่) โดยไม่มีจุดเข้า/SL/TP
  แต่ยังไม่มีข้อยกเว้นที่รับรองชัดเจน ต้องสอบถาม ก.ล.ต. (สายด่วน 1207) หรือทนายหลักทรัพย์

  แจกจ่ายแบบสด 29,280 USD/ปี, แบบหน่วง ≥ 10 นาที 21,840 USD/ปี,
  ผู้ใช้รายย่อยแบบสด 1.55 USD/เดือน/คน (ราคาบนสุด) หรือ 12.10 USD (ความลึก), แบบหน่วงไม่คิดรายคน
* ห้ามแสดงข้อมูลสดบนเว็บสาธารณะ ส่วนหลังล็อกอินถือเป็นการแจกจ่ายให้สมาชิก
  [Schedule 5](https://www.cmegroup.com/market-data/files/Schedule5-v5.0.pdf)
* ข้อมูล TradingView ใช้ในแอปเก็บเงินไม่ได้ (Terms ข้อ 3) [TradingView policies](https://www.tradingview.com/policies/)
* สรุป: ราคา COMEX ในแอปมีต้นทุนขั้นต่ำราว 7–10 แสนบาทต่อปีก่อนมีลูกค้า

### 4.4 PDPA
* ต้องมีประกาศความเป็นส่วนตัวก่อนเก็บข้อมูล (ม.23) ข้อมูลที่จำเป็นต่อสัญญา (บัญชี, อีเมล, การเรียกเก็บเงิน)
  ไม่ต้องขอความยินยอม แต่การตลาดต้องขอแยก (ม.19, ม.24)
* แจ้งเหตุข้อมูลรั่วต่อ สคส. ภายใน 72 ชม. (ม.37(4)) · ต้องมี DPO เมื่อมีเจ้าของข้อมูล ≥ 100,000 ราย
* ส่งข้อมูลไปต่างประเทศ (เช่น server หรือผู้รับชำระเงินต่างประเทศ) ต้องมีมาตรการคุ้มครองตาม ม.28
  [PDPA (แปลอังกฤษ)](https://pdpa.msu.ac.th/wp-content/uploads/2022/05/EN-PDPA-2019.pdf) ·
  [Tilleke เรื่อง DPO](https://www.tilleke.com/insights/thailand-releases-notification-on-data-protection-officer-appointment/)

### 4.5 รับชำระเงินและแจ้งเตือน

  (ลูกค้าต้องสแกนจ่ายทุกเดือน) และธุรกิจ "investment/financial services" ต้องได้รับอนุมัติก่อน

### 4.6 สิ่งที่ปรับในแผนเพราะข้อ 4.1–4.3
* ระยะ 0–1 (เก็บข้อมูลและ backtest เพื่อใช้เอง) ทำต่อได้ตามแผน
* ก่อนเบต้าที่ให้คนนอกใช้ แม้ไม่เก็บเงิน: ต้องได้คำตอบจาก Binance เรื่อง data license
  และจากทนายเรื่องใบอนุญาต
* ร่างอีเมลขอ license ไม่รวมในเอกสารนี้ (เจ้าของขอไม่ให้ร่างจดหมาย) ช่องทางติดต่อ CME คือ
  marketdata@cmegroup.com ส่วน Binance ยังไม่พบช่องทางขอ license ที่เผยแพร่

## 6. เรื่องที่เจ้าของต้องตัดสินใจ

1. ✅ **ตำแหน่งสินค้า:** ตัดสินใจแล้ว (18 ต.ค. 2026) ขายเป็น **เครื่องมือวิเคราะห์** ไม่มีจุดเข้า/SL/TP
   แผนเทรดและบันทึกผลในหน้า desk ใช้ส่วนตัวเท่านั้น ระยะ 1 จะวัดว่าสัญญาณวิเคราะห์ (กำแพง, ไม้ใหญ่, CVD, OI)
   มีประโยชน์จริงไหม แทนการวัดผลแผนเทรด ยังต้องให้ทนายยืนยันขอบเขตตามข้อ 4.1
2. **แหล่งข้อมูล:** ขอ license จาก Binance, หาผู้ขายข้อมูลคริปโตที่อนุญาตให้แสดงต่อสมาชิก หรือใช้ตลาดอื่น
   (ยังไม่ได้ตรวจเงื่อนไขของ exchange อื่นและข้อมูลทองคำฟิวเจอร์สของ TFEX ซึ่งน่าจะตรงกับลูกค้าไทยกว่า)
3. **ราคาทอง COMEX:** จ่าย 7–10 แสนบาทต่อปี หรือไม่แสดง COMEX ในแอป
4. **ผู้รับชำระเงิน:** Omise (ตัดบัตรรายเดือน + PromptPay รายครั้ง) หรือ Stripe (ต้องผ่านการอนุมัติประเภทธุรกิจ)
5. **นิติบุคคล งบประมาณ และผู้ดูแล server**
6. **ชื่อแบรนด์และโดเมน** ห้ามคล้าย thetrader.co.th และห้ามใช้ชื่อ Binance ในการตลาด
